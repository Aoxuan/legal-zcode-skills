# 合同审批风险预审技能

本技能作为合同审批流里**「系统风险预审」节点**的审批人(一个固定员工账号)。它扫描该账号在合同审批定义下的**待办任务**,从表单企业控件(外部选项单选,值「名称｜统一社会信用代码｜法定代表人」;字段为「客户名称」「供应商名称」「达人企业名称」三者之一,互斥、必现其一)读取对方企业三要素。**先做合同主体一致性校验**(2026-10-19 口径,见下段),一致才进入风险查询:**先查 MySQL 近 N 天(默认 90 天)缓存**,命中则零成本复用;未命中先查 **dim_company 判定自然人**——对方是个人则不查企查查,回填「自然人无须评估风险」;是企业才调企查查风险接口、落快照、写 MySQL,并生成 Excel 风险报告。随后用 `tasks/approve` 的 `form` 回填**【企业风险评级】文本字段**;**低/中/高风险**均把 Excel 报告写入 **「风险报告附件」控件(attachmentV2,专用控件)**:两控件**只保留本技能写入的内容**——附件控件整体设值为 `[报告code]`,申请人误传的文件**一并删除**;未知/自然人/兜底不附报告,但若申请人误传过文件则**清空**该控件(清空被飞书拒绝时去掉清空条目重试放行,降级为提醒,不阻塞)。随后**同意放行**给法务节点。

**合同主体一致性校验(2026-10-19,业务反馈驱动;同日三次修正)**:业务方可能表单选的供应商与合同文件里实际签约的对方主体不一致,此时风险查询无效。企业实例在查缓存/企查查**之前**下载「合同附件」Word,解析签约抬头(**统一按「签约主体」排除法**——合作方常自行占据甲方位,方向规则不可靠):解析甲/乙/丙多方主体后,排除 ①与我方「签约主体」匹配的侧 ②**自然人主体**——达人姓名可能是花名(如「阿min学姐」),不能拿表单控件比对,改用**公司类关键词启发式**(名称含 公司/工作室/中心/集团/事务所或英文 LIMITED/LTD 等视为公司,不含视为自然人);剩余**唯一公司主体**即对方,与表单企业名归一化比对(NFKC 全半角归一+包含式);**排除后仅剩自然人**(合同对方是个人而表单企业控件填了企业)→形态不符直接拒绝。**一致**才继续风险查询;**不一致/形态不符直接 `tasks/reject` 拒绝退回**(评论注明合同签约对方与表单字段值,自然人带「（自然人）」标记),不查企查查零计费,飞书自动向发起人推拒绝通知(reject 不支持 form 回填,评级字段不动);**附件缺失/下载失败/解析失败(图片等)/排除后剩 0 或 ≥2 公司主体**→不查企查查、approve 放行,【企业风险评级】回填「合同主体未能自动校验，请法务人工核对」交法务人工。提取口径(实测修订模式合同与两个漏拒案例后定):覆盖 body 全部段落**含表格内**;段落文本取全部 w:t——天然等同「接受所有修订」视图(修订插入的名称可见、被删旧名不出现,python-docx≥1.1);支持签署栏**同行多抬头**与**标题前缀**(「补充协议二甲方：X乙方：Y」);**角色词字符间容空白**(两端对齐排版会把「丙方」拉成「丙    方」,202610190120 漏丙方根因);**旧版 .doc(OLE2)走 UTF-16LE 全文件扫描**(202610190113 根因,抬头与正文粘连按连续空白截断);**文本型 PDF(Word 导出)走 pdfplumber 逐页提取**(仅支持带文本层的 PDF;扫描型无文本层→人工核对兜底,不做 OCR;实测 Word 导出 PDF 提取结果与 docx 一致);清洗剥【】〔〕模板占位括号与并列占位段,未填「【】」视为该侧缺失。`FEISHU_SUBJECT_CHECK=0` 关闭校验回到旧行为。

预审节点**除主体不一致外一律同意放行**:高/中/低风险都交给法务人工判断,不自动拦截。表单企业字段为必填,正常不会为空;若取不到企业或缺三要素,【企业风险评级】回填兜底文案「企业名称为空,风险查询接口不适用」并照常放行。**实例表单无任何企业控件时(如达人解约/达人签约且「是否涉及达人公司」=否,企业控件为条件显示;已核实「达人企业名称」仅在=是时显示)免扫描直接放行**(2026-09-08 口径):不查企查查/不判自然人,【企业风险评级】回填「无须风险扫描（无合作企业）」,实例与定义表单都定位不到评级控件时仅评论放行。
开发源为仓库内 `法务合同签约技能/skills/legal-approval-risk/`;本目录是可安装发行副本。

## 前置:凭据与依赖

首次使用前必须配齐(只需一次)。本机需要 **Python 3.11**(Windows 与 macOS 均可)。下文 `py` 在 macOS 上换成 `python3`。

1. 探测:Windows 跑 `py --version`,macOS 跑 `python3 --version`。没有命令或不是 3.11 → 停下来,把 [INSTALL.md](INSTALL.md) 交给用户。不要开浏览器下载,也不要在用户未确认时静默安装系统软件。
2. 把本文件夹放入平台 skills 目录(zcode / Cursor / Hermes 相同)。
3. 复制 `.env.example` 为 `.env`。**向用户索取**并写入下列凭据,缺则不要硬跑:
   - 飞书自建应用 `FEISHU_APP_ID` / `FEISHU_APP_SECRET`
   - 合同审批定义 `FEISHU_APPROVAL_CODES`(多个用逗号分隔;**默认/正式流程**,普通 poll 只扫它)
   - 测试流程码 `FEISHU_APPROVAL_CODES_TEST`(可选,多个逗号分隔;仅 `poll --test` 扫它。2026-10-27 双流程口径:**默认走正式,只有用户指令里明确带「测试」字样才加 `--test`**;未配置时 `--test` 直接报错,不回退正式码。两流程控件按名称定位,widget id 不同无影响)
   - 表单候选企业控件 `FEISHU_FIELD_COMPANY`(多个逗号分隔:`客户名称,供应商名称,达人企业名称`,三者互斥、必现其一;三要素从命中的外部选项一并取出,不读「对方负责人」)
   - 回填控件 `FEISHU_FIELD_RATING`(默认 `企业风险评级`)、`FEISHU_FIELD_ATTACHMENT`(默认 `附件`)
   - 合同主体校验(默认开):`FEISHU_SUBJECT_CHECK`(0=关)、`FEISHU_FIELD_CONTRACT_ATTACH`(默认 `合同附件`)、`FEISHU_FIELD_OUR_ENTITY`(默认 `签约主体`)
   - 预审审批账号 `FEISHU_APPROVER_USER_ID`(其 `open_id`;未填则回退 `FEISHU_COMMENT_USER_ID`)
   - 缓存窗口 `FEISHU_CACHE_DAYS`(默认 `90`)
   - 企查查 `QCC_APP_KEY` / `QCC_SECRET_KEY`(客户账号,全部接口走这一套)
   - 远程 MySQL `MYSQL_HOST` / `MYSQL_PORT` / `MYSQL_USER` / `MYSQL_PASSWORD` / `MYSQL_DB`
4. 安装依赖:`py -m pip install -r requirements.txt`(macOS 用 `python3 -m pip ...`)。外网不通时用内网代理 `http://docker-proxy.xgate.com/simple`。
5. 自检:`py scripts/poll.py check`。飞书 token + 审批 code + 企查查 + MySQL + 预审账号均就绪才算通过。

缺 Python 指向 [INSTALL.md](INSTALL.md);缺凭据则按 `.env.example` 向用户逐项索取并写入技能根目录 `.env`。不要把密钥写进对话记录或提交到 git。

### 飞书侧准备(管理员须先做)

**审批定义改造(关键)**:在合同审批定义里新增**「系统风险预审」节点**,审批人 = 预审员工账号,排在法务节点之前;在该节点把**【企业风险评级】设为非必填 + 可编辑**、把**附件目标控件(FEISHU_FIELD_ATTACHMENT,当前为「风险报告附件」专用控件)设为可编辑**。没有这个节点,API 无处回填字段(飞书原生审批只能在「同意某审批任务」时用 `form` 写表单控件值,没有单独改实例字段的接口;附件控件也是整体设值,技能写入的内容会替换控件里已有值——该控件为技能专用,申请人误传的文件会被一并删除)。

**应用权限**(自建应用开通后**保存 → 创建版本 → 发布 → 管理员审批**):

- `approval:approval.list:readonly`(查询实例列表,兼容保留)
- `approval:approval:readonly`(实例详情)
- `approval:task`(同意/拒绝任务,**本技能回填字段必需**)
- `approval:task:list_by_user`(查询用户待办任务,或 `approval:approval:readonly`)
- `contact:user.id:readonly`(手机号/邮箱反查 open_id)

预审账号必须带 `FEISHU_APPROVER_USER_ID`(及 `FEISHU_APPROVER_USER_ID_TYPE`,默认 `open_id`)。没有现成 `open_id` 时,向用户要**手机号或个人邮箱**(不要企业邮箱);`FEISHU_APP_ID` / `FEISHU_APP_SECRET` 已写入 `.env` 后,用 `tenant_access_token` 调 `POST /open-apis/contact/v3/users/batch_get_id?user_id_type=open_id`,把返回的 `open_id` 写入 `.env` 的 `FEISHU_APPROVER_USER_ID`。不要把手机号/邮箱写入对话以外的文件,不要提交 `.env`。查不到则提示检查 `contact:user.id:readonly` 已发版,且该账号在应用通讯录权限范围内。

## 工作流程

### 一次性体检

```
py scripts/poll.py check
```

输出 `{ok, report, mysql_connected, feishu_token, approval_codes}`。`ok != true` 时把 `error` 用自然语言转告用户,按缺失项补 `.env`,不要暴露堆栈。

### 干跑一条已知实例(验收,不 approve)

```
py scripts/poll.py test-instance <instance_code>
```

输出 `{ok, instance_code, status, exempt, companies, company, profile, rating_text, subject_check, located_controls, form_preview, approve:false}`。用于确认表单字段映射、回填控件定位(【企业风险评级】/「附件」的 id+type)与风险结果,再开正式轮询。干跑**缓存优先**(不强制查企查查),不上传附件、不 approve/reject。`exempt=true`(无企业控件)时 `rating_text` 为免扫描文案;`subject_check` 为合同主体校验结果(`{status: match|mismatch|skip|off|person, contract_subject, our_entity, reason}`,`mismatch` 时正式 poll 将拒绝退回,干跑仅提示)。

### 补处理单条实例(始终缓存优先,--force 强制重查)

```
py scripts/poll.py process-instance <instance_code> [--force]
```

在预审账号待办里找到该实例并 approve 回填。`--force` 忽略缓存强制重查企查查。

### 一趟扫描(loop 每次触发跑这一条)

```
py scripts/poll.py poll [--test]
```

输出 `{ok, scanned, new, processed, errors, dry_run, approval_codes, approver_user_id}`。

- 扫描对象:预审账号在 `FEISHU_APPROVAL_CODES` 下的**待办任务**(`tasks/query`,`topic=1`),按 `instance_code` 去重
- **双流程口径(2026-10-27)**:普通 `poll` 扫 `FEISHU_APPROVAL_CODES`(正式);`poll --test` 只扫 `FEISHU_APPROVAL_CODES_TEST`(测试),不回退正式码——**用户指令含「测试」字样才加 `--test`**,其余一律普通 poll
- `processed`:本趟已 approve/reject 回填的实例,含 `field`/`risk_level`/`rating_text`/`source`/`cost`/`report_file`/`file_code`/`approved`/`rejected`/`subject_check`
- **合同主体校验先行(2026-10-19)**:企业实例先下载合同 Word 比对签约对方主体——`mismatch` 直接 `tasks/reject` 拒绝退回(零计费,审批意见说明原因);`skip`(附件缺失/解析失败/无法唯一确定)不查企查查、回填「合同主体未能自动校验，请法务人工核对」放行;自然人/缺三要素/开关关闭不校验
- 缓存优先:`FEISHU_CACHE_DAYS`(默认 90)内有记录则复用 MySQL,零成本;未命中先查 dim_company 判自然人(是→回填「自然人无须评估风险」,0 元),是企业才查企查查(约 7.50 元/家)并落库
- 免扫描直接放行:实例表单无任何企业控件(如达人解约/达人签约且不涉及达人公司)时不查企查查/不判自然人,【企业风险评级】回填「无须风险扫描（无合作企业）」(定位不到评级控件时仅评论放行),`risk_level=exempt`、0 元
- 回填:`tasks/approve` 的 `form` 仅含本节点可编辑的【企业风险评级】文本控件;**低/中/高风险**均写「风险报告附件」控件(整体设值只放报告,申请人误传文件一并删除);未知/自然人/兜底不附报告、但误传过文件则清空;同意后流转给法务
- `poll --force` 忽略缓存强制重查企查查后再回填 approve(`--force` 不影响合同主体校验,校验始终执行)
- `.env` 设 `FEISHU_COMMENT_DRY_RUN=1` 时只取风险、不 approve/reject、不记 state
- 幂等(2026-10-19 补多节点口径):approve/reject 后任务从待办消失,天然不重复;**多节点流程下预审账号可能也在后续人工会签节点的待办里**——state.json 已记录的实例直接跳过(输出 `skipped_processed`,**技能不代签人工审批节点**),`process-instance` 对已预审实例返回 `already_processed` 提示;失败下趟重试(已查的企业走缓存,不重复计费)

向用户展示时用自然语言摘要:扫了几条、approve 了几条、风险等级各是什么、有无错误。高风险只作提示,是否继续由审批人判断。

### 用 zcode loop 定时跑

轮询宿主是法务本机:关机即停、错过某个时间点跳过可接受。默认建议每天 10:00 / 14:00 / 16:00,或固定间隔(如 4 小时)。

用户说「开始轮询 / 定时扫审批风险」时:

1. 先跑一次 `check`,不通过则停下来补凭据。
2. 再立刻跑一次 `poll`,把摘要回报。
3. 用 loop 按约定间隔重复:`/loop 4h 运行 legal-approval-risk 的 poll 命令并把结果摘要告诉我`。
4. 用户说停则停止 loop,不要再武装下一拍。

不要在技能内部 `sleep` 死循环;调度由 zcode loop(或用户本机任务计划)负责。

## 风险分级口径

与 `legal-company-query` 相同,`RULES_VERSION=legal-draft-2026-08-13`:

- **高风险**:失信/被执行/破产/限高/股权冻结/严重违法、行政处罚(法务裁定)、三要素不一致、登记状态含吊销/注销/停业/撤销/清算中;裁判文书累计≥10或近12个月被告≥3;开庭公告累计≥10;立案累计≥5。
- **中风险**:未移出的经营异常、环保处罚、动产抵押/股权出质/清算/欠税/税务非正常/税收违法/司法拍卖/公安通告;近24个月裁判文书且为被告、近24个月开庭公告、近24个月立案且为被告。
- **低风险**:以上均未命中。
- **未知**:查无此企业或数据不存在。
- **自然人**:缓存未命中后查 dim_company 判定(表单信用代码为身份证号,或该行 `source=自然人信息录入申请表单`/代码为身份证号)。自然人**不查企查查、不附报告、不做合同主体校验**。
- **免扫描(exempt)**:实例表单无任何企业控件(如达人解约/达人签约且「是否涉及达人公司」=否;企业控件为条件显示,控件存在但值为空同样视为未出现)。**不查企查查、不判自然人、不附报告**,误传过文件则清空附件控件。
- **主体不一致(subject_mismatch,2026-10-19)**:合同 Word 签约对方主体与表单企业控件不一致。**不查企查查、不附报告、`tasks/reject` 拒绝退回**(reject 不支持 form 回填,评级字段不动,原因写审批意见)。
- **主体未核验(subject_unverified,2026-10-19)**:合同附件缺失/下载失败/解析失败/无法唯一确定对方主体。不查企查查、不附报告,回填「合同主体未能自动校验，请法务人工核对」后放行交法务人工。

回填到【企业风险评级】的文本:`高风险，详见风险报告附件` / `中风险，详见风险报告附件` / `低风险` / `未知（未查得风险数据）` / `自然人无须评估风险` / 无企业控件时 `无须风险扫描（无合作企业）` / 主体未核验时 `合同主体未能自动校验，请法务人工核对`;企业控件有值但缺三要素时填 `企业名称为空,风险查询接口不适用`(2026-09-04 口径:低/中/高风险均附 Excel 报告到「风险报告附件」控件)。主体不一致时被拒,无回填。

## 注意事项

- **不做企业匹配**:表单已有准确企业(外部选项),直接 `profile`,不调 `search`/886。
- **字段名验收**:新表单上线或改字段名后,先用 `test-instance` 干跑一条真实实例,确认 `companies` 命中正确字段、`located_controls` 命中【企业风险评级】与「附件」控件;字段名配错会导致回填控件定位失败。
- **回填控件模糊定位**:控件名先精确后模糊匹配(模糊=控件名**完全包含**配置名,配置名 ≥4 字)——`FEISHU_FIELD_ATTACHMENT` 只需配「风险报告附件」稳定前缀,正式部署调整括号内说明不影响定位;控件名缺字或短于配置不匹配,过短配置(如默认「附件」)不做模糊兜底,避免误中「合同附件」。
- **回填控件须可编辑**:【企业风险评级】与附件目标控件必须在「系统风险预审」节点设为可编辑,否则 `tasks/approve` 的 `form` 写入会被忽略或报错。
- **控件独占口径(2026-09-04)**:【企业风险评级】与「风险报告附件」只保留本技能写入的内容;申请人误写误传一律删除(误传文件在无报告场景也会清空)。清空若被飞书拒绝,降级为放行+`attachment_warning` 提醒人工删除,不阻塞审批。
- **计费**:仅缓存未命中且为**企业**时查企查查(约 7.50 元/家);90 天内同企业复用缓存,自然人/免扫描实例 0 元。人工查询/缓存复用请用 `legal-company-query`。
- **审批评论**:同意时评论 `风险预审完成：<评级>，自动放行`(评级=低风险/中风险/高风险/未知（未查得风险数据）/自然人无须评估风险;免扫描实例为 `风险预审完成：无合作企业，无须风险扫描，自动放行`;主体未核验为 `风险预审完成：合同主体未能自动校验，请法务人工核对，自动放行`;缺三要素兜底时为 `风险预审完成，自动放行`);主体不一致拒绝时评论 `风险预审拒绝：合同签约对方为「X」，与表单{字段}「Y」不一致，请核对修改后重新提交（未查询企业风险）`。
- **合同主体校验依赖**:`requirements.txt` 含 `python-docx`(docx 解析)与 `pdfplumber`(文本型 PDF 提取);附件直链 12 小时有效、下载无需鉴权;支持 .docx / 旧版 .doc(UTF-16LE 扫描) / 文本型 PDF(Word 导出);扫描型 PDF 与图片无文本层,走「主体未核验」放行提醒(不做 OCR)。
- **报告高亮**:Excel 报告中命中风险的指标行整行黄色高亮(概要区附「高亮说明」图例);登记状态正常存续、三要素一致不高亮。
- **数据合规**:企查查数据仅用于内部风控,不得二次分发。快照与 Excel 落在技能内 `data/snapshots/`,查询结果写远程 MySQL,已 approve 实例记在 `data/state.json`。
- **错误处理**:脚本输出 `{ok:false,error}` 时把 `error` 转告用户,不要暴露原始堆栈或密钥。
